# Философия и архитектура

## Откуда растёт проблема

Стандартный PHP-шаблон получает данные через ассоциативный массив. Это удобно пока проект маленький — быстро, гибко, без лишних движений. Но за этой гибкостью скрыта цена: IDE не знает что внутри массива, PHPStan не может проверить ключи, опечатка обнаруживается только в браузере. Шаблон — это чёрный ящик, который принимает всё и ни за что не отвечает.

```php
$view->render('card', ['titl' => $title, 'prise' => $price]); // ошибки — в рантайме
```

Со временем проект растёт, компонентов становится больше, в команду приходят новые люди. И начинается: никто не знает что именно нужно передать в шаблон, документация устарела или не существует, рефакторинг превращается в угадывание.

Blade и Twig решают часть проблем — дают синтаксис, наследование, секции. Но фундаментальную проблему не решают: данные по-прежнему передаются как неструктурированный массив, CSS и JS живут отдельно, а компонент как таковой не существует — есть просто файл с разметкой.

---

## Компонент — это класс

Центральная идея Brick проста: если компонент — это класс, то все инструменты которые умеют работать с классами начинают работать с компонентами.

```php
class Card extends Brick
{
    public function __construct(
        public string $title,
        public int $price,
        public bool $inStock = true,
    ) {}
}
```

Этот класс — контракт. Он говорит: чтобы отрендерить карточку, нужны `title`, `price` и опционально `inStock`. Всё. Не массив с неизвестными ключами, не документация которая может устареть — живой PHP-код который проверяется компилятором.

IDE видит свойства и подсказывает их в шаблоне. PHPStan анализирует `template.php` так же строго, как любой другой код. Рефакторинг свойства — и все места использования подсвечиваются сразу. Новый разработчик открывает класс и мгновенно понимает что нужно компоненту.

---

## Всё в одном месте

Второй принцип: всё что относится к компоненту живёт рядом.

```
Card/
  Card.php        ← контракт
  template.php    ← разметка
  style.css       ← стили
  script.js       ← поведение
```

Это не просто организационное решение — это архитектурное. Компонент становится самодостаточной единицей. Его можно перенести в другой проект, опубликовать как пакет, удалить без поиска по всему проекту где лежат его стили. Связность внутри компонента высокая, зависимость от окружения — минимальная.

## Иммутабельность как гарантия

Базовый класс `Brick` объявлен как `readonly`. За этим стоит конкретная причина: HTML-рендеринг должен быть детерминированным.

Иммутабельный компонент с одинаковыми данными **всегда** вернёт одинаковый HTML. Это означает:

- Рендер можно безопасно кэшировать — не нужно думать об инвалидации при изменении состояния, потому что состояния нет
- Параллельный рендеринг безопасен — нет общего мутабельного состояния, нет race condition
- Тесты предсказуемы — результат зависит только от входных данных, а не от порядка запуска

Мутабельный аналог `Clay` существует для случаев когда иммутабельность невозможна — например при интеграции с легаси-кодом. Но это осознанный выбор с явными предупреждениями, а не дефолтное поведение.

---

## Явное лучше неявного

Brick намеренно не использует магию: никакой авторегистрации через DI-контейнер, никаких атрибутов, никаких конфигурационных файлов. Создал класс в директории — он работает. Вся конфигурация компонента видна в одном месте.

Это делает систему предсказуемой. Любой разработчик, знакомый с PHP, может разобраться в компоненте не зная ничего о Brick — просто читая код.

---

## Контракт как проклятие и преимущество

Строгий контракт — это осознанный trade-off. Ассоциативный массив мягкий: добавил ключ, и всё работает. Класс жёсткий: добавил свойство — иди обновляй все места создания компонента.

На маленьком проекте это иногда раздражает. На большом — спасает. Когда PHP-компилятор сам находит все места где нужно внести изменения, рефакторинг перестаёт быть страшным. Когда PHPStan проверяет шаблоны, целый класс ошибок исчезает до деплоя.

Brick делает ставку на долгосрочную надёжность в ущерб краткосрочной гибкости. Это сознательный выбор — не для всех проектов и не для всех команд, но для тех кто его делает осознанно.
